= Logging & Monitoring

Dshackle can log all requests to a file in JSON format.
Or https://jsonlines.org/[JSON Lines] to be more precise, i.e., a test file where each line is a JSON.

It includes:

- _Access Log_ - requests made to Dshackle from a client
- _Request Log_ - requests made by Dshackle to an upstream

Because some requests may produce multiple responses, or multiple internal requests the log is not related as one-to-one.
But instead maintains a reference a `request.id` in both logs, that can be used to join multiple access and request logs into a single trace.

== Access Log

NOTE: By default, the Access log is disabled.

To enable access log add following configuration:

[source,yaml]
----
access-log:
  enabled: true
  filename: /var/log/dshackle/access_log.jsonl
----

`filename` is optional, and the default value is `access_log.jsonl` (i.e., in the current directory).

Or if you use a centralized log processor listening a socket:

[source,yaml]
----
access-log:
  enabled: true
  type: socket
  host: 127.0.0.1
  port: 9000
----

In this case all logs sent to the `127.0.0.1:9000` socket via TCP, and each line is prefixed with a 32 bit length.

Since a single request may contain multiple replies (ex., a batch call, or subscribe to the head blocks) the Dshackle logging is based on replies.
The access log file contains details per each response send from the server, and each of them refers to original request details.

The log contains the JSON lines similar to:

[source,json]
----
{
  "version":"accesslog/v1beta2",
  "id":"578d83db-cf53-4ef8-b73e-3f1cc0a67e96",
  "channel":"DSHACKLE",
  "ts":"2021-07-20T01:53:33.174645Z",
  "method":"NativeCall",
  "blockchain":"ETHEREUM",
  "total":2,
  "index":0,
  "succeed":true,
  "request":{
    "id":"513b9b49-b472-4c83-b4b7-58dd2aabe9f6",
    "start":"2021-07-20T01:53:33.086946Z",
    "remote":{
      "ips":["127.0.0.1", "10.0.5.102", "172.217.8.78"],
      "ip":"172.217.8.78",
      "userAgent":"grpc-node-js/1.1.8"
    }
  },
  "nativeCall":{
     "method":"eth_blockNumber",
     "id":2,
     "payloadSizeBytes":2
  }
}
----

.Where:
- `version` version of the JSON format (note it may change until `v1`, i.e., a version with `alpha`, `beta`, etc., is not a final format)
- `id` uniq id of the reply
- `channel` access channel (`DSHACKLE` for native Dshackle calls, `JSONRPC` for JSON RPC HTTP Proxy)
- `ts` timestamp of the reply
- `method` Dshackle method which was called (i.e., not a Blockchain API method, see `nativeCall` details)
- `blockchain` blockchain code
- `total` how many requests in the batch (available only for a `NativeCall` call)
- `index` current index (i.e. count) of the reply to the original request
- `succeed` if call succeeded, in terms of Blockchain API
- `request` original request details
** `id` uniq id of the request; all replied to the same request have same id
** `start` when request was received
** `remote` remote details
*** `ips` list of all recognized IPs (including headers such as `X-Real-IP` and `X-Forwarded-For`)
*** `ip` a single ip, that likely represent a real IP of the remote
*** `userAgent` user agent
- `nativeCall` details of the individual Native Call request
** `method` method name terms of Blockchain API
** `id` request id provided in the original request
** `payloadSizeBytes` size of the original _individual_ request (for JSON RPC it's size of the `params` value)

== Request Log

NOTE: By default, the request log is disabled.

To enable request log add following configuration:

[source,yaml]
----
request-log:
  enabled: true
  filename: /var/log/dshackle/request_log.jsonl
----

Could use the same config as Access Log for sockets:

[source,yaml]
----
request-log:
  enabled: true
  type: socket
  host: 127.0.0.1
  port: 9000
----

The log contains the JSON lines similar to:

[source,json]
----
{
  "version":"requestlog/v1alpha",
  "id":"c23a5391-1b8c-40b0-a32f-fa736b8175a2",
  "success":true,
  "upstream":{
    "id":"sepolia",
    "channel":"WSJSONRPC",
    "type":"JSONRPC"
  },
  "request":{
    "source":"INTERNAL",
    "id":"f2ae5096-b7d0-4006-99c5-0108bd295df4",
    "start":"2022-11-09T01:13:25.652663Z"
  },
  "jsonrpc":{
    "method":"eth_getBlockByHash",
    "id":218
  },
  "blockchain":"TESTNET_SEPOLIA",
  "execute":"2022-11-09T01:13:25.540592Z",
  "complete":"2022-11-09T01:13:25.652683Z",
  "responseSize":6243,
  "queueTime":0,
  "requestTime":112
}
----

.Where:
- `version` version of the JSON format (note it may change until `v1`, i.e., a version with `alpha`, `beta`, etc., is not a final format)
- `id` uniq id of the request
- `success` if it returns a result or an error
- `upstream` upstream reference
** `id` id as defined in upstreams config
** `channel` type of the connection (`WSJSONRPC` for a Websocket JSON RPC, `JSONRPC` for HTTP JSON RPC, `DSHACKLE` for Dshackle protocol)
** `type` type of the request (`DSHACKLE` for Dshackle gRPC request, `JSONRPC` as JSON RPC, and `WSSUBSCRIBE` Websocket subscription request)
- `request` reference to original request
** `source` is `REQUEST` when is caused by external call, or `INTERNAL` if it's an internal request such as a health check
** `id` for a `REQUEST` source it's the same id as in access log in `request.id` field.
For an `INTERNAL` source it's just an internal id.
** `start` time when the request was initiated (note that the execution time may differ, see below)
- `jsonrpc` details about the JSON RPC request (optional)
- `blockchain` blockchain associated with the request (optional)
- `execute` time when the request started to execute.
Some request may consist of multiple additional requests, or a request may wait until other requests are returned.
So it may be after the `request.start` time.
- `complete` time when the response was received from upstream.
- `responseSize` response payload size in bytes (payload here means it's not the whole json but only the _result_ part).
- `queueTime` - the time between _start_ and _execute_ moments, in milliseconds
- `requestTime` - the time between _execute_ and _complete_ moments, in milliseconds

== Prometheus Metrics

By default, Dshackle provides Prometheus metrics on `http://127.0.0.1:8081/metrics`.

To configure the metrics use:

[source,yaml]
----
monitoring:
  enabled: true
  jvm: false
  extended: false
  prometheus:
    enabled: true
    bind: 192.168.0.1
    port: 8000
    path: /status/prometheus
----

Where `jvm` options enabled monitoring of the JVM internals, such as memory, GC, threads, etc.
And `extended` enables additional metrics for query selectors, etc.

Requests are measured on both sides of Dshackle:

- _downstream_ - the requests clients make to Dshackle, `dshackle_downstream_*`
- _upstream_ - the requests Dshackle makes to its upstreams, `dshackle_upstream_*`

One downstream request can lead to none (e.g., answered from cache), one, or several (retries, quorum) upstream requests.
And Dshackle makes upstream requests of its own, for validation and head polling.

=== Downstream Requests

The requests clients make to Dshackle are measured with labels:

- `protocol` - how the client reached Dshackle: `dshackle` (Dshackle's own gRPC API), `http-json-rpc` or `ws-json-rpc` (the JSON RPC proxy over HTTP or WebSocket)
- `method` - the gRPC method, e.g. `nativeCall`, `subscribeHead` or `getBalance`.
A JSON RPC call is a `nativeCall`, whether it came through the proxy or as an item of a gRPC `NativeCall`, and an `eth_subscribe` over WebSocket is a `nativeSubscribe`.
With `extended` monitoring, a JSON RPC call is labeled with its own method instead, e.g. `eth_call`, or `unsupported` for a method the blockchain doesn't serve.
- `chain` - the blockchain, e.g. `ETH`, or `NA` when the request isn't for one chain
- `status` - how the request ended (only for `dshackle_downstream_requests_total`):
** `success` - answered with a result. For a subscription, it means it started.
** `error` - answered with an error that belongs to the request, e.g. a reverted call, invalid parameters, an unsupported method, or a transaction the node rejected
** `failed` - Dshackle couldn't serve it, e.g. no upstream was available or all of them failed
** `rate-limited` - every upstream that could serve it was at its <<04-upstream-config.adoc#request-limits,request limits>>

[cols="2a,5"]
|===
| Metric | Description

| `dshackle_downstream_requests_total`
| Number of requests, by `status`.
Each item of a gRPC `NativeCall` counts as a request, also when the whole `NativeCall` is refused.

| `dshackle_downstream_request_duration_seconds`
| Time to process a request and respond, up to its first result for a response that streams several.
Not measured for subscriptions.

| `dshackle_downstream_subscription_messages_total`
| Number of messages pushed to subscriptions
|===

NOTE: These replace the legacy `dshackle_request_jsonrpc_*` and `dshackle_request_grpc_*` metrics, which had the protocol in the name.

=== Upstream Requests

The requests Dshackle makes to its upstreams are measured per upstream, with labels:

- `upstream` - the upstream id
- `chain` - the blockchain, e.g. `ETH`
- `protocol` - the connection the request went through: `http-json-rpc` (JSON RPC over HTTP), `ws-json-rpc` (JSON RPC over WebSocket), `dshackle` (a remote Dshackle), or `internal` when Dshackle settled the request itself without sending it
- `status` - how the request ended (only for `dshackle_upstream_requests_total`):
** `success` - the upstream answered with a result
** `error` - the upstream answered with a JSON RPC error, e.g. a reverted call or invalid parameters.
That includes an error the node sent with an HTTP error status, e.g. Bitcoin's `500` "Already Spent".
** `failed` - no usable answer: connection error, timeout, an HTTP error from a struggling provider (`401`, `429`, `502`-`504`) or without a JSON RPC error, invalid response, or the upstream said it's overloaded.
A request abandoned before the upstream answered, e.g. by a validation timeout or a client that left, is `failed` too.
** `rate-limited` - the request was refused by the request limits.
With `protocol="internal"` it's the upstream's own <<04-upstream-config.adoc#request-limits,`limits`>>, and nothing was sent.
With `protocol="dshackle"` it's the remote Dshackle refusing it because all its upstreams are at their limits.

[cols="2a,5"]
|===
| Metric | Description

| `dshackle_upstream_requests_total`
| Number of requests to the upstream, by `status`

| `dshackle_upstream_request_duration_seconds`
| Time the upstream took to answer a request (`success` or `error`)

| `dshackle_upstream_response_size_bytes`
| Size of the results the upstream answered with

| `dshackle_upstream_requests_in_flight`
| Number of requests sent to the upstream and not yet answered
|===

Validation and head polling over HTTP are counted too, as they're requests to the same upstream.

NOTE: These replace the legacy `dshackle_upstream_rpc_*`, `dshackle_upstream_ws_*` and `dshackle_upstream_grpc_*` metrics, which had the protocol in the name.

=== Upstream State

The current state of the upstreams, taken on each scrape.

[cols="2a,1a,5"]
|===
| Metric | Labels | Description

| `dshackle_upstream_availability`
| `chain`, `status`
| Number of a chain's upstreams in each availability status (`ok`, `lagging`, `immature`, `syncing`, `unavailable`).
Summed over `status`, it's the number of the chain's upstreams.

| `dshackle_upstream_lag`
| `chain`, `upstream`
| How many blocks the upstream is behind the chain head

| `dshackle_upstream_height`
| `chain`, `upstream`
| Current head height of the upstream
|===

NOTE: These replace the legacy `dshackle_upstreams_*` metrics. The legacy `dshackle_upstreams_connected` is gone, as it was the sum of `dshackle_upstream_availability`.

=== Fork Choice

[cols="2a,1a,5"]
|===
| Metric | Labels | Description

| `dshackle_forkwatch_status_total`
| `chain`, `status`
| Number of upstream blocks the chain's fork choice classified, by verdict: `new`, `outrun`, `equal`, `fallbehind` or `rejected`
|===

NOTE: It replaces the legacy `dshackle_forkwatch_status_bychain_total`, which also had the fork choice as a `type` label, and the statuses in uppercase.

=== Log Pipeline

Only with `extended` monitoring.
The `log` label tells the two logs apart: `access` or `request`.

[cols="2a,5"]
|===
| Metric | Description

| `dshackle_logs_produced_total`
| Log events produced

| `dshackle_logs_written_total`
| Log events written to the log target

| `dshackle_logs_dropped_total`
| Log events dropped without writing, because the queue was full

| `dshackle_logs_queue_size`
| Log events waiting to be written
|===

NOTE: These replace the legacy `dshackle_monitoringLogs_*` metrics.

== Health Checks

Dshackle provides a http endpoint to check status of the servers.
This check is compatible with https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/#http-probes[Kubernetes Liveness and Readiness Probes].

By default, it's disabled, and you have to set up which blockchain are required to be available to consider Dshackle alive.

.Example config:
[source,yaml]
----
health:
  port: 8082 # <1>
  host: 127.0.0.1 # <2>
  path: /health # <3>
  blockchains: # <4>
    - chain: ethereum # <5>
      min-available: 2 # <6>
    - chain: bitcoin
      min-available: 1
----

<1> (optional) port to bind the Health server.
Default: `8082`
<2> (optional) host to bind the Health server.
Default: `127.0.0.1`
<3> (optional) path on the server.
Default: `/health`.
I.e., `http://127.0.0.1:8082/health` with default config
<4> list of blockchain to check availability
<5> a Blockchain to check
<6> minimum available (i.e., fully synced) Upstreams for that blockchain

With the config above the server is considered healthy if:

- Dshackle has connected to at least two valid Ethereum upstreams
- **and** at least one valid Bitcoin upstream.

When the server is healthy is responds with `OK` and 200 as HTTP Status Code.
When any of the checks failed, it responds with a short description and 503 as HTTP Status Code.

Example of a response for an unhealthy server that doesn't have enough upstreams for a Ethereum Classic Blockchain.

.GET http://127.0.0.1:8082/health
----
ETHEREUM_CLASSIC UNAVAILABLE
----

Optionally, the server can be called with `?detailed` query, which provides a more detailed response:

.GET http://127.0.0.1:8082/health?detailed
----
ETHEREUM_CLASSIC UNAVAILABLE
BITCOIN AVAILABLE
  local-btc-1 OK with lag=0
ETHEREUM AVAILABLE
  local-eth-1 OK with lag=0
  local-eth-2 OK with lag=0
----
